## 2. Build methods and lessons

| ID / method | Creator practice reported in the article | Application to our work |
|---|---|---|
| M01 — Structure | Animator creator researched state management and component communication. | Define data, screens, states, and relationships before expanding features; explicitly relate questions, answers, claims, sources, and observations. |
| M02 — Dialogue | Animator grew through conversation and experimentation. | Begin with one working flow; use observed results to choose the next refinement. |
| M03 — Revert | Returning to an earlier version could help when a bug or crash resisted fixes. | Keep checkpoints and try a different approach when repeated patches degrade the result. |
| M04 — Sketch | Web poetry and Moxy started with paper sketches. | Sketch the critical interaction and screen sequence before generation. |
| M05 — Design first | Web poetry's sketches became Figma designs before Make. | Use the current approved design as deliberate context; verify the latest version first. |
| M06 — Behavioral detail | Web poetry's prompt specifies hover, completion, typing, and transitions. | State each trigger and observable result, including return and recovery behavior. |
| M07 — Visual explanation | Moxy used sketches to explain handle resizing/movement. | Attach an annotated sketch when spatial behavior is ambiguous in words. |
| M08 — Modularity | Moxy requested separate components, files, and folders. | Separate evidence viewer, source panel, navigation, and data handling; likewise workflow selection and brief editing. |
| M09 — Clarification | Moxy asked the AI to clarify unclear input. | Resolve ambiguities that change business meaning or behavior; use judgment for routine choices. |
| M10 — Code continuation | Moxy's creator described downloading code and continuing in an editor. | Evaluate a production handoff after verifying current export capabilities and inspecting generated code. |
| M11 — Chat-first exploration | Weather Synthesizer began in conversation without a design file. | Use dialogue for novel interaction experiments and design context for visual consistency. |
| M12 — Real data | Weather Synthesizer used APIs for functioning behavior. | Add data when it tests an important assumption; label live, simulated, and illustrative parts. |
| M13 — Early testing | Trip planner used working prototypes to discover pain points. | Test comprehension and navigation before expanding the site. |
| M14 — Responsive testing | Trip planner refined layouts across browsers and screen sizes. | Test complete desktop/mobile flows, expanded content, and navigation. |
| M15 — Design system | Package Customizer began with tokens, components, clear frame names, and consistent constraints. | Apply shared type, spacing, color, controls, and layout rules across iterations. |
| M16 — Small prompts | Package Customizer's creators preferred shorter prompts for easier refinement. | Give each refinement one bounded objective and verify it before continuing. |
| M17 — Prompt history | Package Customizer retained prompt versions. | Record important prompts, resulting changes, and checks alongside versions. |
| M18 — Other testers | Web poetry's creator emphasized repeated testing and friends trying the app. | Ask representative visitors to perform a task without coaching and observe misunderstandings. |

The article reports approximate prompt counts: animator initially two, then about 80 more; Web poetry 90; Moxy 800; Weather Synthesizer 150; trip planner 250; Package Customizer 450. These are context, not productivity benchmarks or recommended budgets. Short prompts are one reported preference, not proof that shorter is universally better.

The starting prompts ranged from a broad configurator request to detailed interaction behavior and precise reproduction of a supplied screen. Our choice: provide a sufficiently complete initial brief, then refine in small, testable steps. Do not turn one maker's technique into a universal rule.

## 3. Proposed first applications

### MindLeverX: claim-to-source evidence explorer

Start with the existing fictional Example Studio content after checking the live file. A visitor selects a claim in an example answer; the matching source excerpt and status appear while the answer remains visible. Preserve explicit fictional-example labels and distinguish supported from unresolved claims. Missing evidence must not become a positive verification badge.

States: initial example; selected supported claim; unresolved claim; return to full answer. Use curated records for the first slice. This does not require a live AI request.

Success check: a new visitor can identify one supported claim, one unresolved claim, and the source of that distinction without help. Check keyboard operation, mobile layout, focus, and readable labels. These checks do not establish full accessibility conformance.

Recent local notes said claim disclosure was not implemented. That is historical context, not a fresh inspection. The existing proposition was “Know what AI says. See what backs it up.”

### Augmind: opportunity configurator

Use the proposed Art of the Possible method as context. A visitor selects a representative workflow and desired outcome, explores a clearly labeled illustrative possibility, and edits a short opportunity brief.

States: workflow choice; illustrative current/possible process; outcome and constraints; editable brief; next-step invitation. Include the opportunity, affected people, intended outcome, unknowns, and the next discovery question. Do not invent savings, ROI, feasibility, or completed analysis.

Success check: the visitor can explain the opportunity and identify what remains to validate. This is a small taste of discovery, not validation of the complete workshop method or a promise of a particular engagement deliverable.

### Shared working sequence

1. Check the latest frames, copy, and project decisions; preserve earlier work.
2. Sketch one complete interaction and define its states and data.
3. Prototype that slice with labeled example data and a coherent design system.
4. Refine one behavior/component per prompt; retain useful versions.
5. Test comprehension, keyboard use, mobile layout, and applicable empty/error states.
6. Add real integrations only after checking the relevant current documentation, authorized data, operating requirements, and usefulness.

Suggested first slice: MindLeverX claim disclosure because existing example content may offer a bounded starting point. This is a recommendation, not an approved implementation order. No existing design, live site, or integration was changed in this article review.

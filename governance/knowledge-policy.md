# Knowledge policy

Our maintenance rules, based on the [owner-approved source practice snapshot](official-source-build-practice.md). The live owner file named in the manifest should be re-read when available; the snapshot records the policy used for this edition.

## Keep claim types distinct

- **Requirement:** identify the standard/platform, exact provision, version, level, scope and exceptions.
- **Recommendation:** identify the responsible source and why the advice applies.
- **Project choice:** state the selected behavior and its rationale; do not attribute our synthesis to an external authority.
- **Hypothesis:** state the uncertain explanation and what evidence could disconfirm it.
- **Observation/result:** preserve test conditions, method, result and limitations separately from the proposed remedy.

Evidence status and implementation status are separate. A verified finding can have an untested remedy. A proposed study is not a result. A source citation is not a measurement of this website.

## Update procedure

1. Inspect current project state before reusing a dated site finding.
2. Locate the relevant source record and inspect its scope and retrieval limitations.
3. Recheck changeable official guidance before a consequential implementation, release or purchase. Do not advance the check date merely because a file was copied or summarized.
4. Add observations and decisions using stable IDs and the templates. Link the evidence and source IDs.
5. If evidence changes a conclusion, mark the old conclusion superseded and link the replacement. Keep historical evidence rather than silently rewriting it as if it had always agreed.
6. Update the readable catalogs and JSON records together, and add a dated changelog entry.

Version 1.0 source check dates come from the earlier research records. Organization itself did not re-fetch those sources. ISO access was limited to public catalog descriptions. Failed or uninspected research is noted in the evidence files and must not be promoted into verified knowledge.

## Maintenance boundaries

Keep general methods in the library, project-specific findings in records, and historical evidence in evidence/. Do not export local project findings as universal design rules. A future public package should review project names, local paths, permission to share material, and source attribution. This collection summarizes sources and links to them; it does not redistribute full third-party publications.

The import manifest is immutable provenance for version 1.0. If a library document changes later, retain its original import hash and record the revision in ../CHANGELOG.md; the old hash then describes the imported version, not the new file.
